# Открытые вопросы: справки и оправданные отсутствия

Решения до реализации. Закрытые пункты помечать `[x]` и кратко фиксировать ответ.

## Уже решено

### Scope и контур

- [x] **Проверка в ЕМИАС / внешних базах** — вне продукта. Сотрудник проверяет сам; ЛК только решение и период.
- [x] **Кампусы** — `HEAD` / `KAZAN` / `KRASNODAR`, как отчёты отсутствующих.
- [x] **Dev** — студенты/родители только из `app.preview.student-ids` (`previewEnabled`).
- [x] **Права админов** — отдельные секции по филиалам при создании учётки.
- [x] **Cutoff** — 21:00 Europe/Moscow. Одобрение до 21:00 → исключение из мониторинга на дни периода.

### Продукт (ответы 2026-03-26)

- [x] **Кто подаёт** — и студент, и родитель (за ребёнка из своей сессии).
- [x] **Типы** — больничный, освобождение от военкомата, **прочее**.
- [x] **Период дат** — указывает **только админ при одобрении** (студент/родитель период не задаёт).
- [x] **Отклонение** — причина **обязательна** и **видна** студенту/родителю.
- [x] **Пересечения** — можно подавать ещё заявки на пересекающиеся даты (в т.ч. пока другая PENDING/APPROVED).
- [x] **Уведомления** — делаем: студенту/родителю при одобрении и отклонении (канал как у остальных уведомлений ЛК — email и/или MAX по доступности); админу о новой заявке — тоже (детали канала в tech design).

### Отчёт и период

- [x] **После 21:00** — уже собранный отчёт за сегодня **не правим**. Период действует на **будущие** дни (следующие сборки). День `D`, если одобрили после cutoff сборки за `D`, в уже готовый отчёт за `D` не вмешиваемся.
- [x] **Модель периода** — период хранится **на одобренной заявке** (`approved_from` / `approved_to`) и при **новой** сборке отчёта читается оттуда. Отдельную сущность «календарь» и правку строк старого отчёта **не делаем** на этапе 1.  
  *(Пояснение: это и был вопрос «отдельная таблица или поля на заявке» — выбран простой вариант: поля на заявке.)*
- [x] **Программы обучения** — период действует на **студента целиком в рамках кампуса заявки**, без выбора программы (бакалавриат/СПО и т.п.). Отчёт отсутствующих и так строится по студенту кампуса, не по отдельной программе.  
  *(Пояснение: «программа» = запись обучения из 1С в профиле; отдельный выбор не нужен.)*
- [x] **Гранулярность** — только **полные календарные дни**.

### Техника

- [x] **Файлы** — PDF, JPG, PNG, HEIC; до **50 МБ** на файл.  
  - Изображения (JPG/PNG/HEIC): нормализация/сжатие **как у фото пропуска** (`PassPhotoValidationService.normalizeForStorage` — downscale + JPEG quality).  
  - PDF: **полный размер**, без перекодирования.  
  - Число вложений: минимум 1; несколько — допустимо в разумных пределах (зафиксировать в реализации, по умолчанию до 5).
- [x] **Хранение** — как сейчас у фото пропуска: **локальный диск / Docker volume** (`storageDir`), отдельный каталог для справок (например `app.certificates.storage-dir`). S3 не обязателен на этапе 1; при росте объёма — тот же интерфейс storage можно сменить. Для prod этого достаточно при бэкапе volume.
- [x] **Админ UI** — **три отдельных раздела** (Голова / Казань / Краснодар). В очередь раздела попадают только заявки студентов соответствующего филиала; exclusion работает для отчёта отсутствующих **того же** филиала.
- [x] **Кампус заявки** — **автоматически из профиля** студента (как для кабинетной аналитики / филиала); пользователь не выбирает.

## Мелочи (закрыто 2026-03-26)
